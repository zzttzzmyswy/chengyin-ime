# 质量与性能基线（审查 R11 第一阶段）

本文件是迭代 I03 的交付物：给共享核心建立**可复现的输入质量与微基准基线**。
本阶段只建立基线，不优化词库、排序或算法；所有数字都是“当前状态”的测量值，不是达标声明。

## 一、复现命令

```sh
# 1. 质量基线（独立标注集，只测共享核心）
cargo run --release -p myswy-core --example quality_report --locked

# 2. 核心微基准（逐键 / 候选标记 / 编辑 / 翻页）
MYSWY_BENCH_ROUNDS=1000 cargo bench -p myswy-core --bench latency --locked

# 3. 标注集结构门禁（含开发/测试集不重叠的自动检查）
cargo test -p myswy-core --test quality_corpus --locked

# 4. 重新生成标注集（确定性）
python3 scripts/generate_eval_corpus.py
```

原始输出：`build/quality-baseline.txt`、`build/bench-i03-baseline.txt`。

## 二、标注集来源与许可

标注集在 `data/eval/quality.tsv`，共 488 条，由 `scripts/generate_eval_corpus.py`
从仓库已有、已固定修订的数据生成，**没有引入任何新的第三方语料**：

| 来源 | 许可 | 在标注集中的用法 |
| --- | --- | --- |
| `data/daily.tsv`（Rime pinyin-simp 固定修订 + jieba） | Apache-2.0 + MIT，见 `data/README.md` | 提供全部拼音、文字与词频 |
| 本脚本自写规则 | 本仓库 MIT | 派生模糊音、键盘失误、组合长句、学习场景 |

- 不读取、不依赖任何真实用户输入历史；不含个人词库或学习记录。
- 生成是确定性的：种子固定、依赖已固定的 `data/daily.tsv`，因此 sha256 可复现
  （当前 `data/eval/quality.tsv` = `c60814e250a47694c06888bf9eececd03b4299acd37972978ccd0caf2eb970d5`）。
- 语料自身是**评测用**的，不是训练语料；生成脚本不做任何引擎优化。

## 三、标注集设计

列：`category split flags input expected train bucket note`。

- **开发/测试分离**：按输入的 ASCII 拼音串做 SHA-256 取模分半，因此**同一个输入串
  不会同时出现在两个半集**；生成器发现交集会直接失败。`crates/ime-core/tests/quality_corpus.rs`
  在正常测试套件里再次独立校验这一点（自动门禁）。
- **`expected` 口径**：取该拼音在词库中词频最高的那个读法（`sc` 类同）。所以 Top-1
  衡量的是“引擎是否把本词库自己排第一的读法排在第一位”，不是主观挑稀有同音词。
  唯一的例外是 `initials`（见下）与 `in;deep` 探针，二者在 `bucket` 中显式标注。
- **`input` 口径**：默认不带撇号的连续拼音（实际输入的主流写法）；`initials` 类为
  一字一首字母；`fuzzy`/`typo` 类直接是**用户在混淆下实际敲出的串**，`flags` 精确打开
  被考察的那一条规则位。
- **`train`**：`record:<拼音>=><文字>`，表示宿主**已经确认**的选词，评测前写入 profile。
  未收录文字按定义不会出现在候选页上，因此只能按已确认选择写入（与平台适配器加载
  已存 profile 走同一个入口），不能通过翻页选中。

### 九个类别与难度分档（每类 dev/test 各半）

| 类别 | 每集条数 | 难度分档 | 考什么 |
| --- | ---: | --- | --- |
| `whole_word` | 30 | 词频 high/mid/low | 2–3 音节整词首选 |
| `single_char` | 30 | 同音字数 1–5 / 6–20 / 21+ | 完整单音节下的字词一致性与同音压力 |
| `long_sentence` | 15 | 字数 4–6 | 长句组合（含词典条目与多词组合） |
| `homophone` | 20 | 首二词频差 ≤2× / ≤4× | 存在真实竞争同音词时的首选 |
| `fuzzy` | 4 × 11 规则 | 每条 `an->ang` 等 | 11 组模糊音各自独立覆盖 |
| `typo` | 10 × 4 类 | swap/omit/neighbor/repeat | 四类键盘失误各自独立覆盖 |
| `initials` | 20 | `in;top` / `in;deep` | 1–多字首拼：首选正确性 + 深层词可达性与翻页代价 |
| `prefix` | 15 | 前缀音节数 2 / 3 | 前缀选择（前缀本身自成词，且存在更长词） |
| `learning` | 10 × 3 场景 | 提出/一向/三向 | 长期学习：见证提权、无据三选提权、单次不劫持 |

`initials` 的 `expected` 不能取“某个拼写的首选”：一个首拼键会被**所有音节首字母相同的
拼写**共享。例如 `bm` 同时指向 `bu'men`（部门）、`bang'mang`（帮忙）、`bi'mian`（避免）
等 97 个条目；`cp` 同时指向 `chan'pin`（产品）、`chang'pian`（唱片）等 65 个。
若只认其中一个拼写的首选词，Top-1 就被“该拼写恰好是常用那个”的概率封顶，不是引擎能力。
因此该类改为：`in;top` 取**该键在词库中词频最高的词**（公平首选口径）；`in;deep` 取同键
最深处的词，其 Top-1 天然为 0，只用于看 `可达` 与 `按键`。这一修正把首拼 Top-1 从
被低估的 27.5% 修回 90.0%。

各分档样本数与实测结果见 `build/quality-baseline.txt` 的 `by difficulty bucket` 段。

## 四、质量基线（硬件与语料）

- 硬件：13.24 开发机，Intel Core i9-10900X 10C/20T @3.70 GHz，251 GiB 内存，
  Arch Linux，kernel 7.2.7-zen1，governor `performance`。
- 词库：`data/daily.mswydict`，87,540 条，
  SHA-256 `b218e5a87acdc1a8b6f586d1c6c31442b2d5a1075fd797265a4b5cccf8676af9`；
  源 TSV `data/daily.tsv` SHA-256 `0b3386677e7f98c047a4f839d878b78cb54f0671611b8e3b8a1583189573eb88`。
- Rust 1.98.0，release（thin LTO）。单进程测量，不含 UI/TSF/磁盘。
- 指标口径：`top1` = 首位候选命中；`top9` = 第一页命中；`full` = 200 页内可达；
  `combo` = 首位是合成组合（词频为 0）而非词库条目；`wrongCombo` = 首位是合成组合
  且不是期望文字（错误组合率）；`keys` = 键入键数 + 翻页键数 + 选择键。

### 已确认的缺口（本阶段只记录，不修复）

1. **首拼对深层词无效**：`in;top`（37 条）Top-1 97.3%、Top-9 100%，说明“该键最高频词
   排第一”基本成立；但 `in;deep`（同键最稀有词，3 条）Top-1 与 Top-9 均为 0%、
   可达 100%、2 字键按键 P50 10。即**能翻到，但翻得很深**，是排序/深度问题而非
   覆盖率问题，也是后续优化最直接的靶子。
2. **`long_sentence` 有 1 条不可达**：组合句 `doushiziji` 期望“都是自己”，引擎在
   200 页内不提供该串（实测给出“斗士子集 / 都是 …”等）。该行记入 `full=96.7%`，
   属于引擎覆盖缺口，不是标注错误。
3. **模糊音的规则间差异大**：`in->ing` 25%、`f->h` 50%、`n->l` 50%、`zh->z` 62.5%
   对 `an->ang`、`ch->c`、`en->eng`、`l->r` 的 100%；且 `in->ing`、`n->l` 出现
   合成组合抢占首位（错误组合率 25%/12.5%）。
4. **`typo` 的 omit / swap 最弱**：omit 60%、swap 80%，且 swap 的可达只有 80%
   （4 条翻不到期望文字），弱于 neighbor 95% 与 repeat 100%。
5. **按键 P95 偏高**：`long_sentence` 15，与翻页深度一致；优化排序可直接降低。

### 解读与限制

- 本轮**首次补齐“中段编辑”**这一项（R11 明确要求逐键、候选标记、编辑、翻页分别测量）。
- 编辑键 P50 为 190 ns，但 P95 已是 1.52 ms：分布双峰，说明少数编辑位置（触发重解析）
  与多数廉价移动键（Left/Right/Home/End）混在同一组。**不能把 P50 当作编辑代价**。
- 绝对数值明显高于本仓库历史上 Windows/Ryzen 9950X 的记录（见 `docs/PERFORMANCE.md`），
  这是**不同机器**：i9-10900X 与 Ryzen 9 9950X 不同代不同频。跨机器数值不可直接比较；
  本表只作为 13.24 上的**同机基线**，后续优化必须与同机、同轮重放对比。
- 机器不是专用基准机：后台有其他负载（采样时 load average ≈ 2）。同轮重复运行结果稳定
  （P50 波动 <1%），但**不宣称尾延迟达标**。
- 单键目标 ≤0.5 ms、加载 ≤50 ms 仍未达成；全规则长串逐键 P99 达 25.5 ms，远高于目标。
  本阶段只建立基线并给出剖析方向，不做优化。

## 六、下一步（留给优化迭代，不在本阶段）

按收益排序：首拼深层词排序（`in;deep` 可达但翻页深）→ `in->ing`/`n->l` 等模糊规则的
首选与错误组合率 → typo omit/swap 的召回 → 长串逐键 P99 剖析（当前 25.5 ms）。
